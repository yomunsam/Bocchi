# 部署与运维

Bocchi Home Server 是带管理后台的服务，适合放在家庭服务器、NAS 或个人 VPS 上，前面加一层反向代理提供 HTTPS。它生成的静态站点另外发布到 Nginx、GitHub Pages 这类静态托管上，Home Server 本身不需要对公网开放。

本文介绍两种部署方式（Docker 和直接运行发布包），以及反向代理、备份恢复、升级和在同一台机器上跑两个站点的做法。

## 数据目录

Bocchi 的全部状态都放在一个数据目录（DataRoot）里。开发环境下默认用项目里的 `.bocchi-dev-data`；其他环境必须显式指定一个绝对路径，没有指定或者写了相对路径时，程序会直接报错退出，不会悄悄在程序目录旁边建一个。

用环境变量或配置文件都可以指定：

```bash
# 环境变量（Linux / macOS）
export Bocchi__DataRoot=/srv/bocchi/data
```

```json
// appsettings.Production.json
{
  "Bocchi": {
    "DataRoot": "/srv/bocchi/data"
  }
}
```

Docker 镜像已经把 DataRoot 设为 `/data`，挂一个卷上去即可。

数据目录里各部分的用途：

| 路径 | 内容 | 需要备份 |
| --- | --- | --- |
| `state/bocchi.sqlite` | 账户、站点设置、发布配置、构建记录等 | 是 |
| `keys/` | ASP.NET Core Data Protection 密钥 | 是，见下文 |
| `workspace/` | 内容工作区（文章、页面、媒体等，是一个 Git 仓库） | 是 |
| `themes/`、`state/theme-config/` | 已安装的 Theme 和它们的配置 | 是 |
| `cache/`、`output/`、`logs/` | 构建缓存、生成结果、日志 | 否，可以重新生成 |
| `backups/` | 备份文件和迁移前的数据库快照 | 建议另外拷到别处 |

### keys 目录

数据库里保存的 GitHub token、OAuth client secret、发布凭据等，都用 `keys/` 里的密钥加密。Bocchi 固定了 Data Protection 的应用名，所以换安装目录、升级二进制或者换新容器都不影响解密。

密钥丢了就没法补救：数据库还在，但里面加密过的 token 和 secret 都解不开，需要在后台重新填写，所有人也要重新登录。备份时 `keys/` 必须和 `state/bocchi.sqlite` 一起带上（下面的 `backup` 命令会自动包含）。

这些密钥以明文 XML 存放，没有额外加密。数据目录的访问权限要收紧，备份文件也按敏感数据保管。

## 用 Docker 部署

镜像发布在 `ghcr.io/yomunsam/bocchi`，支持 amd64 和 arm64。仓库里的 [Deploy/compose.yaml](../../../Deploy/compose.yaml) 是一个可以直接改的示例：

```yaml
services:
  bocchi:
    image: ghcr.io/yomunsam/bocchi:${BOCCHI_VERSION:?请设置 BOCCHI_VERSION，例如 0.1.0}
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:8080"
    environment:
      Bocchi__ReverseProxy__TrustedProxies: "172.31.250.1"
    networks:
      - bocchi
    volumes:
      - bocchi-data:/data

networks:
  bocchi:
    ipam:
      config:
        - subnet: 172.31.250.0/24
          gateway: 172.31.250.1

volumes:
  bocchi-data:
```

启动后在本机打开 `http://127.0.0.1:8080`，会进入安装向导。

```bash
BOCCHI_VERSION=0.1.0 docker compose -f Deploy/compose.yaml up -d
```

也可以把 `BOCCHI_VERSION=0.1.0` 写进 compose 文件旁边的 `.env`，之后的 `docker compose` 命令都会读到它。

几点说明：

- 容器里的程序以非 root 用户 `app`（UID 1654）运行，监听 8080 端口。
- 端口只绑定到 `127.0.0.1`，由同一台机器上的反向代理对外提供 HTTPS。
- 用命名卷时权限会自动处理。改成绑定宿主机目录的话，先把目录属主改成 1654：`sudo chown -R 1654:1654 /srv/bocchi/data`。
- 镜像没有 `latest` 标签，版本号必须写明。没设置 `BOCCHI_VERSION` 时 compose 会直接报错。
- 想从源码构建，把 compose 里的 `image` 换成 `build: { context: .. }`。仓库根目录的 `Dockerfile` 会顺带构建管理后台的前端资源。
- 使用 `process` Runner 的 Theme 需要的 Node.js 等工具链，镜像里没有。这类 Theme 要基于官方镜像自行扩展。

## 直接运行发布包

[GitHub Releases](https://github.com/yomunsam/Bocchi/releases) 提供 `linux-x64`、`linux-arm64` 和 `win-x64` 的自包含包，解压就能运行，不需要另装 .NET。

```bash
tar -xzf bocchi-0.1.0-linux-x64.tar.gz
cd bocchi-0.1.0-linux-x64
Bocchi__DataRoot=/srv/bocchi/data ./Bocchi.HomeServer
```

默认只监听 `http://127.0.0.1:5081`。要换地址，设置 `Kestrel__Endpoints__Http__Url`，例如 `http://0.0.0.0:5081`。

长期运行建议交给 systemd：

```ini
# /etc/systemd/system/bocchi.service
[Unit]
Description=Bocchi Home Server
After=network.target

[Service]
User=bocchi
WorkingDirectory=/opt/bocchi
ExecStart=/opt/bocchi/Bocchi.HomeServer
Environment=Bocchi__DataRoot=/srv/bocchi/data
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

程序目录里不保存任何状态，升级时整个替换即可，放到带版本号的新目录也没问题。

## 反向代理

管理后台用的是 Blazor Server，反向代理需要支持 WebSocket。代理负责 HTTPS，并通过 `X-Forwarded-For`、`X-Forwarded-Proto`、`X-Forwarded-Host` 把原始请求的信息转给 Bocchi。

Bocchi 只信任来自指定地址的转发头。不在名单里的来源即使带了这些头也会被忽略，这样别人没法伪造来源地址或协议。名单用 `Bocchi:ReverseProxy:TrustedProxies` 配置，可以写单个 IP 或 CIDR 网段，用逗号、分号或空格隔开：

```bash
Bocchi__ReverseProxy__TrustedProxies="172.17.0.1, 10.0.0.0/8"
```

本机回环地址（`127.0.0.1`、`::1`）默认就是可信的，所以代理和 Bocchi 装在同一台机器、直接连 `127.0.0.1` 时，不用额外配置。

Docker 是例外。宿主机上的代理连进容器时，容器看到的来源是所在 Docker 网络的网关地址，不是回环地址。compose 示例给 Bocchi 建了一个固定网段 `172.31.250.0/24` 的网络，网关固定为 `172.31.250.1`，所以只信任这一个地址，同机其他容器伪造的转发头不会被采纳。这个网段和本机已有网络冲突时，把 `subnet`、`gateway` 和 `TrustedProxies` 一起改掉。

代理本身也跑在容器里时，让它加入同一个网络，并用 `ipv4_address` 给它固定一个地址，再把这个地址写进 `TrustedProxies`。

信任名单配错时，常见现象是安装向导或登录表单提交后返回 400。原因是 Bocchi 看到的仍是 `http` 和内部地址，和浏览器发来的 `https` 来源对不上。

### Caddy

Caddy 会自动申请证书、处理 WebSocket，并设置上面三个转发头：

```caddyfile
blog-admin.example.com {
	reverse_proxy 127.0.0.1:8080
}
```

### Nginx

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 443 ssl;
    http2 on;
    server_name blog-admin.example.com;

    ssl_certificate     /etc/ssl/blog-admin.example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/blog-admin.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;
    }
}
```

管理后台不需要对公网开放。可以只在内网或 VPN（比如 Tailscale、WireGuard）里访问，或者在代理上加一层访问限制。

## 备份与恢复

程序自带两个维护命令，在服务启动之前执行，跑完就退出。命令和服务一样靠 `Bocchi__DataRoot` 找数据目录，所以要显式带上。

下面以上文 systemd 的配置为例（程序在 `/opt/bocchi`，服务用户是 `bocchi`）：

```bash
cd /opt/bocchi

# 备份，默认写到 <数据目录>/backups/bocchi-backup-<时间>.zip
sudo -u bocchi env Bocchi__DataRoot=/srv/bocchi/data ./Bocchi.HomeServer backup
sudo -u bocchi env Bocchi__DataRoot=/srv/bocchi/data ./Bocchi.HomeServer backup --output=/mnt/nas/bocchi.zip

# 恢复，先停服务
sudo systemctl stop bocchi
sudo -u bocchi env Bocchi__DataRoot=/srv/bocchi/data ./Bocchi.HomeServer restore /mnt/nas/bocchi.zip --force
sudo systemctl start bocchi
```

请用服务用户执行这两个命令。用 root 跑的话，写进数据目录的文件归 root 所有，服务重启后会因为没有权限读写而出错。`--output` 指向的目录和要恢复的备份包，也要让服务用户能访问。

备份包里有数据库的一致性快照、`keys/`、内容工作区、已安装的 Theme 和其他状态文件，不包括缓存、生成结果、日志和 `backups/` 本身。数据库用 SQLite 的在线备份接口导出，服务运行时也可以执行 `backup`。

恢复前必须先停掉服务。服务运行时会锁住数据目录（`.bocchi.lock`），这时执行 `restore` 会直接报错退出；同一个数据目录也不能同时起两个服务。数据目录里已经有数据时，`restore` 会拒绝执行，需要加 `--force`。加了以后，它会先把现有数据另存为 `bocchi-before-restore-<时间>.zip`，再清空并解压。`cache/` 和 `output/` 每次恢复都会清空，恢复后第一次发布会完整重新构建。备份包来自旧版本也没关系，下次启动时会自动迁移数据库。

在 Docker 里，参数直接跟在服务名后面：

```bash
# 备份，然后把文件拷到宿主机
docker compose -f Deploy/compose.yaml run --rm bocchi backup
docker compose -f Deploy/compose.yaml cp bocchi:/data/backups/ ./bocchi-backups/

# 恢复
docker compose -f Deploy/compose.yaml stop bocchi
docker compose -f Deploy/compose.yaml run --rm \
  -v "$PWD/bocchi.zip:/import/bocchi.zip:ro" bocchi restore /import/bocchi.zip --force
docker compose -f Deploy/compose.yaml start bocchi
```

默认的备份位置在数据目录里面，和数据在同一块盘上，防不了磁盘损坏。定期把 `backups/` 里的文件拷到别的机器或网盘上。

## 升级

Docker 把 `BOCCHI_VERSION` 改成新版本号，拉取镜像后重建容器；发布包直接替换程序目录。数据目录保持不动。

```bash
# 先把 .env 里的 BOCCHI_VERSION 改成新版本
docker compose -f Deploy/compose.yaml pull
docker compose -f Deploy/compose.yaml up -d
```

启动时，如果新版本带了数据库迁移，Bocchi 会先把现有数据库复制到 `backups/database/bocchi-<时间>-pre-migration.sqlite`，再执行迁移。全新安装和没有待执行迁移的启动不会生成快照。快照默认保留最近 5 份，可以用 `Bocchi:Backup:PreMigrationRetainCount` 调整。

迁移出问题时，可以退回升级前的状态：停掉服务，用这份快照替换 `state/bocchi.sqlite`，同时删掉旁边的 `bocchi.sqlite-wal` 和 `bocchi.sqlite-shm`，再换回旧版本的程序启动。

## 在同一台机器上跑两个站点

一个 Bocchi 实例只管一个站点。需要第二个站点时，跑两个实例：两个容器，各自挂自己的 `/data`，由反向代理分到两个子域名。

```yaml
services:
  blog:
    image: ghcr.io/yomunsam/bocchi:${BOCCHI_VERSION:?请设置 BOCCHI_VERSION，例如 0.1.0}
    restart: unless-stopped
    ports:
      - "127.0.0.1:8081:8080"
    environment:
      Bocchi__ReverseProxy__TrustedProxies: "172.31.250.1"
    networks:
      - bocchi
    volumes:
      - blog-data:/data

  notes:
    image: ghcr.io/yomunsam/bocchi:${BOCCHI_VERSION:?请设置 BOCCHI_VERSION，例如 0.1.0}
    restart: unless-stopped
    ports:
      - "127.0.0.1:8082:8080"
    environment:
      Bocchi__ReverseProxy__TrustedProxies: "172.31.250.1"
    networks:
      - bocchi
    volumes:
      - notes-data:/data

networks:
  bocchi:
    ipam:
      config:
        - subnet: 172.31.250.0/24
          gateway: 172.31.250.1

volumes:
  blog-data:
  notes-data:
```

```caddyfile
blog-admin.example.com {
	reverse_proxy 127.0.0.1:8081
}

notes-admin.example.com {
	reverse_proxy 127.0.0.1:8082
}
```

有两点要注意。

1. 不要只靠端口区分两个实例，比如同一个主机名下的 `home.example.com:8081` 和 `home.example.com:8082`。浏览器的 cookie 不区分端口，两个实例的登录 cookie 又同名，登录一个就会把另一个挤掉。每个实例要有自己的主机名。
2. 两个实例都要用 GitHub 登录的话，需要注册两个 OAuth App。GitHub 的 OAuth App 只能填一个回调地址，这里分别是 `https://blog-admin.example.com/signin-github` 和 `https://notes-admin.example.com/signin-github`。

两个实例的数据完全独立：管理员账号、已安装的 Theme 和备份都各管各的，内存也占两份。

## 常用配置

| 配置项 | 环境变量 | 说明 |
| --- | --- | --- |
| `Bocchi:DataRoot` | `Bocchi__DataRoot` | 数据目录，非开发环境必填，必须是绝对路径。镜像内为 `/data` |
| `Bocchi:ReverseProxy:TrustedProxies` | `Bocchi__ReverseProxy__TrustedProxies` | 可信反向代理的 IP 或 CIDR，回环地址始终可信。compose 示例里是固定网络的网关 `172.31.250.1` |
| `Bocchi:Backup:PreMigrationRetainCount` | `Bocchi__Backup__PreMigrationRetainCount` | 迁移前数据库快照保留份数，默认 5 |
| `Kestrel:Endpoints:Http:Url` | `Kestrel__Endpoints__Http__Url` | 监听地址，发布包默认 `http://127.0.0.1:5081`，镜像内为 `http://0.0.0.0:8080` |
